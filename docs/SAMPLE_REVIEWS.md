# U22 디지털 샘플 검토·수정·승인

완료한 자체 합성 U21 후보를 샘플 버전으로 고정하고 조건 검토·의견·수정 요청·보류·승인/철회를 기록한다. `sample_reviews.py`의 로컬 SQLite API와 두 번째 탭의 검토 화면을 연결했다. PAT 부위명 정답 승인이나 기업 인수 기능과 구분한다.

## 사용 흐름

1. 기존 명령 `PYTHONPATH=src python3 -m aurora serve --port 8765`로 실행한다. 기본 Python 표준 라이브러리만 필요하며 U22는 AI 모델을 다시 실행하지 않는다.
2. **디지털 샘플링·라벨링 → 디지털 샘플 검토·수정·승인**에서 합성 작성자 역할을 적용하고 완료한 U21 후보·등록 사유를 선택한다. 저장된 U21 예제와 이 PC의 성공한 새 생성 실행을 모두 찾는다. 공개 ABO 혼합 입력·실패/진행 중 실행·외부 파일/URL은 등록하지 않는다.
3. 작성자가 검토를 요청하면 검토자가 외형·색상·명세 치수 확인·원단 표현 한계·명세 필수 조건을 각각 판정하고 의견을 저장한다. 미충족 항목에는 사유가 필요하다. 치수/원단 항목은 명세와 한계의 검토이며 이미지의 실측·원단 물성 인증이 아니다.
4. 수정 요청에는 작성자가 다른 생성 후보 또는 새 U20 명세의 후보를 새 버전으로 등록한다. 시각 변경과 명세 변경을 별도로 기록한다. 동일 파일·동일 명세를 사유만 바꿔 수정본으로 등록할 수 없다. 픽셀 편집/재생성은 U21에서 수행하며 U22는 그 산출물의 교체/검토를 관리한다.
5. 새 버전을 제출하고 모든 필수 항목을 적합으로 검토한 뒤 별도 승인자가 **가상 디지털 승인**한다. 승인자는 버전/파일·명세와 검토 사건의 해시를 함께 확정한다. 생성 성공만으로 승인하지 않는다.

역할 선택은 **인증이 아닌 합성 시뮬레이션**이다. 개발 PC의 loopback에서 누구나 네 고정 합성 역할을 선택할 수 있다. 서버는 임의 역할 필드를 받지 않고, 8시간 유효한 무작위 세션 토큰을 해시로 보관해 고정 작성자/검토자/승인자/열람자 권한을 검사한다. 토큰은 로컬 브라우저 sessionStorage에만 보관하며 내보내기/Pages에 포함하지 않는다. 실제 사용자 인증·프로젝트 멤버십/RLS·기업 승인 권한을 검증한 기능은 아니다. 기존 Supabase 로그인 상태와 독립적이다.

| 역할 | 합성 데모의 허용 작업 |
|---|---|
| 작성자 | 첫 후보/수정본 등록, 초안·보류본 제출, 의견 |
| 검토자 | 제출본 조건 판정, 수정 요청·보류, 의견 |
| 승인자 | 적합 판정이 끝난 제출본 승인, 검토 중 수정 요청/보류, 승인 철회, 의견 |
| 열람자 | 조회·이력 내보내기 |

## 상태·불변성

초안 → 검토 중 → 승인 / 수정 요청 / 보류. 수정 요청에는 새 수정본이 필요하다. 보류본은 재제출 후 다시 검토한다. 승인자의 승인 철회는 보류 사건으로 이전 승인 해시와 연결한다. 모든 변경에는 의견/사유와 요청 키·현재 이력 순서가 필요하다.

샘플 수정본은 이전 수정본 SHA-256에, 검토 사건은 이전 사건 SHA-256에 연결한다. SQLite 트리거로 수정본/사건 UPDATE·DELETE를 거부한다. 현재 head/이력 순서의 낙관적 동시성 검사와 트랜잭션으로 같은 부모에서의 경쟁 수정을 거부한다. 같은 역할·요청 키의 재전송은 새 사건을 만들지 않는다. **옛 승인 요청의 재전송도 현재 유효성을 다시 계산**하고 원래 접수 순서를 따로 반환하므로, 이전 응답의 승인을 되살리지 않는다.

현재 유효한 승인은 최신 샘플 버전·최신 U20 명세가 일치하고 승인 상태일 때만 표시한다. 수정본에는 이전 승인을 복사하지 않는다. 이전 승인 사건은 이력에 남는다. U20 명세가 바뀌면 새 샘플 등록 전에도 현재 승인 유효성을 false로 계산한다. 변경 시각을 추정한 가짜 사건을 만들지 않으며 최신 명세 해시와 비교해 판단한다. 승인/수정 트랜잭션은 U20 DB를 먼저 잠가 명세 등록과의 경쟁을 막는다.

이력 해시는 손상/일관성 검사이며 전자서명이나 관리자 공격에 대한 부인 방지 수단이 아니다. 로컬 DB 관리자에 대한 접근 통제·백업/서명은 운영 후속 범위다. `manufacturing_verified/effect_measured=false`를 유지하고 기존 U21 생성 보고서의 `design_approved`를 덮어쓰지 않는다. U22의 별도 검토 이력에서 디지털 승인 상태를 조회한다.

## API·저장·내보내기

| 요청 | 계약 |
|---|---|
| GET `/api/sample-reviews/catalog` | 완료한 합성 후보·해시·최신 명세 여부·검토 제품 요약·고정 합성 역할 |
| POST `/api/sample-reviews/session` | `{persona_id}` → 로컬 합성 역할 세션. 실제 로그인 아님 |
| GET `/api/sample-reviews/session` | Bearer 토큰의 고정 합성 역할·만료 확인 |
| POST `/api/sample-reviews/revisions` | 후보 ID/해시·부모 버전·expected_seq·수정 사유·request_key. 작성자 세션 필요 |
| POST `/api/sample-reviews/events` | product_id·version·expected_seq·action·comment·checks·request_key. action별 역할/상태 검사 |
| GET `/api/sample-reviews/products/{product_id}` | 수정본·조건 판정·승인/철회·이전 승인·현재 유효성·해시 연결 |
| GET `/api/sample-reviews/assets/{sha256.ext}` | 등록 당시 복사한 고정 미리보기/GLB만 해시 검사 후 제공 |
| GET `/api/sample-reviews/export/{product_id}` | 전체 이력/해시 검증과 모든 고정 자산 크기/해시 확인 뒤 JSON 내보내기 |

세션 이외 POST는 `Authorization: Bearer ...`를 쓴다. Host/Origin은 기존 loopback 규칙을 따르며 임의 쿼리·중복 JSON 키·비유한 값·알 수 없는 필드를 거부한다. 미로그인/역할 거부403, 낡은 명세/버전/expected_seq와 요청 키 충돌409, 잘못된 조건/상태400이다.

`results/sample-reviews.sqlite3`와 `results/sample-review-assets/`에 로컬로 저장한다. 후보를 등록할 때 실제 파일의 크기/SHA를 재검사하고 내용 해시 이름으로 복사하므로 U21 실행 폴더와 검토 대상이 분리된다. 기존 생성 결과는 보존한다. 회사 원본·외부 업로드는 지원하지 않는다.

Pages의 `client/demo/reviews/`는 저장 조회/내보내기만 가능하다. 실제 상태 전이로 만든 합성 6종·샘플 12버전·거부 사례12건을 제공한다. AI 결과3종과 기하 후보3종을 재사용했으며 새 AI 학습/추론이나 외부 데이터 다운로드는 없다. 공개 버전의 체크리스트·승인 사건은 **프로그램으로 실행한 합성 시나리오**이며 사람/기업의 승인 기록이 아니다.

```sh
# 새 출력 폴더에서 재현; 기존 저장 결과는 덮어쓰지 않음
PYTHONPATH=src python3 tools/build_review_demo.py --output results/new-review-demo
PYTHONPATH=src python3 -m unittest discover -s tests -p 'test_sample_reviews.py' -v
```

실제 사용자 Auth/RLS·기업 승인자, Supabase DS 검토 저장/다중 호스트 운영, 자유로운 원화 편집·U23 패턴/BOM·U24 실제 효과는 후속이다. 기존 DEM 서버 SQL/권한은 이번에 변경하지 않았다.
